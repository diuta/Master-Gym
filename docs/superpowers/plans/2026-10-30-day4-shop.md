# Day 4 — Shop (Inventori, Penjualan, Pembelian, Pengeluaran) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The kasir keeps a product list, buys stock in from suppliers, sells it with split payments and records categorised expenses; the superadmin cancels sales/purchases (stock restored), deletes expenses and manages expense categories.

**Architecture:** New `features/shop/` holds inventory, sales and purchases (they share the stock ledger and the product picker); new `features/expenses/` holds expenses. Each folder has `logic.ts` (pure, tested), `validation.ts` (Zod, tested), `queries.ts`, `actions.ts`. Stock is never stored: it is the sum of `stock_movements`, and every write that reads stock first locks the product rows (`FOR UPDATE`, ascending id) in the same transaction. Sales and purchases write `payments` rows like day 2–3, linked by a new `sale_id` / `purchase_id`.

**Tech Stack:** Next.js 16.4 (App Router, Server Actions, async `searchParams`), React 19, Drizzle 0.45 (`check`, `pgSequence`, `.for("update")`) + drizzle-kit (`db:push`), Postgres 16, Zod 4, vitest 4, shadcn base-nova in `components/ui/`. **No new dependencies.**

**Spec:** [docs/superpowers/specs/2026-10-30-day4-shop-design.md](../specs/2026-10-30-day4-shop-design.md). Read it (sections 4, 5 and 7 are binding) before any task. Sembako reference: `~/Uta/sembako-staging` (`features/inventori/stock-service.ts`, `add-produk-dialog.tsx`, `inventory-table.tsx`, `features/penjualan/penjualan-form.tsx`, `features/pembelian/pembelian-form.tsx`, `produk-combobox.tsx`, `kelola-supplier-dialog.tsx`, `features/keuangan/pengeluaran/`, `components/shared/riwayat-filter.tsx`, `lib/date.ts`). ## Global Constraints

- **Never `git commit` or `git push`.** The user commits manually.
- Before writing Next.js code, check `node_modules/next/dist/docs/` for the API you use (AGENTS.md). Page `searchParams` is a Promise.
- **Never run Prettier** (the repo has no config; the style is ~100 columns, double quotes, semicolons as in surrounding files).
- Code, files, routes, DB in English; every UI string Indonesian.
- Pages in `app/` stay thin: `await requireRole(...)`, load data, render a component from `features/`.
- Every Server Action starts with `requireRole(...)`: `"kasir"` for products, categories of products, suppliers, sales, purchases, adding expenses; `"superadmin"` for cancel sale/purchase, delete expense, expense categories; `"kasir", "superadmin"` only for read actions used by pages both roles see (history detail).
- **The sale price is never taken from the browser.** The server reloads each product; a client `unitPrice` ≠ `products.sale_price` returns `{ message: "Harga sudah berubah, muat ulang halaman." }`.
- **Stock never goes below 0.** Sale: "Stok <nama> tidak cukup: tersedia <n>." Cancel purchase: "Stok <nama> tidak cukup untuk dibatalkan, sebagian sudah terjual." Stock is only ever `sum(stock_movements.qty_delta)`; `stock_movements` is insert-only; cancels never update or delete item rows.
- Payment rows must equal the total exactly (`paymentsMatchPrice` from `features/membership/logic.ts`), in the schema and again on the server against the server-computed total.
- Dates on sale/purchase/expense: `YYYY-MM-DD`, default `todayWib()`, never after `todayWib()` ("Tanggal tidak boleh di masa depan.").
- Money `decimal(14,2)` in DB, whole Rupiah `number` in TS; `avg_cost` is `decimal(14,4)` (store `n.toFixed(4)`). Quantities are integers.
- Reuse, don't copy: `PaymentRows`, `PAYMENT_METHOD_LABELS`, `PaymentMethod`, `ActionResult` (`features/membership/validation.ts` / `payment-rows.tsx`), `todayWib`, `normalizePhone`, `paymentsMatchPrice` (`features/membership/logic.ts`), `rupiah`, `formatDateId` (`lib/format.ts`), `StatusBadge` kinds `in_stock` / `low_stock` / `out_of_stock` / `success` / `cancelled`, `components/ui/wizard.tsx`, the Kelola Paket dialog pattern for CRUD pop-ups. If a membership helper you need isn't exported, export it; don't duplicate it.
- Deleting a used product category, supplier, product or expense category deactivates it; unused rows are deleted.
- Comments only explain *why*. Known-limit shortcuts: `// shortcut: <limit>, <when to upgrade>`.
- UI: text ≥ 16px for things read quickly, 44px targets (`h-11`), full Rupiah via `rupiah.format`, statuses colour + icon + text, confirm (AlertDialog) before delete or cancel. Colour tokens from `app/globals.css` only.
- After adding new server exports, restart `npm run dev` before browser checks (Turbopack keeps stale modules, see HANDOFF section 5).

## Review Focus

1. **Two sales of the last unit at once.** Only one succeeds; the other gets "Stok … tidak cukup". Both lock product rows `FOR UPDATE` in ascending id order before summing the ledger. Pinned in Task 2 (`lockProducts`) and checked by the Task 4 reviewer.
2. **Kasir edits a price while a sale form is open in another tab.** Saving the old form returns "Harga sudah berubah, muat ulang halaman." and writes nothing. Pinned in Task 4 Step 4.
3. **Cancelling a purchase whose items were partly sold, or cancelling twice.** Blocked with the stock message / "Transaksi ini sudah dibatalkan."; nothing written. Pinned in Task 6 Step 4.
4. **Future or malformed dates, zero/negative qty, duplicated product lines.** Rejected by the schemas. Pinned in Task 1 tests.
5. **A product deactivated (or a supplier/category deactivated) while a form is open.** The server rejects: "Produk tidak aktif." / "Supplier tidak aktif." / "Kategori tidak aktif." Pinned in Task 4 Step 4, Task 5 Step 4, Task 7 Step 3.

- `features/shop/stock.ts` (`import "server-only"`):
  - `type Executor` = the transaction type of `db.transaction` (match how `getMemberSummary(id, executor = db)` types it).
  - `lockProducts(tx: Executor, ids: number[]): Promise<Map<number, LockedProduct>>` where `LockedProduct = { id: number; name: string; unit: string; salePrice: number; avgCost: number; isActive: boolean; stock: number }`. Dedup and sort `ids` ascending, `SELECT … FOR UPDATE` the product rows, then one grouped `sum(qty_delta)` for those ids (missing → 0). Why-comment: ascending order prevents deadlocks; summing after the lock sees every committed movement.
  - `stockSubquery()`: a Drizzle subquery `{ productId, stock }` (`coalesce(sum(qty_delta),0)::int`) for list queries to left-join.
